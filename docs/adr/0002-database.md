# 0002. Database

- Status: accepted
- Date: 2026-10-17
- Notion: [ADR 0002: base de datos (PostgreSQL con Kysely, sin ORM ni GraphQL)](https://app.notion.com/p/3fc95e6919c581d28924fae7e108d34f)

## Context

The Game context now has a domain and an application layer with in-memory adapters (ADR 0001). The in-memory repositories kept references to the aggregates, so a use case that forgot to save would still pass its tests. Closing that gap needs the aggregates to become plain data and back, and the shape of that data depends on the database. Deciding the database later would mean redoing the persistence contract.

Forces:

1. The data is relational: dilemmas with immutable versions and linked translations, answers that point to the exact version played, consent with its history, rooms, games and players.
2. GDPR: data in an EU region (Madrid, `europe-southwest1`) and deleting or revoking everything about a player in one place.
3. The research dataset needs queries across games, groups and dilemmas.
4. Listings with filters and text search in seven languages: dilemma catalog, game history, likes.
5. One developer, near-zero cost without players, everything on GCP next to Firebase Auth.
6. The domain stays pure (ADR 0001), and Node runs TypeScript by stripping types, without a build step.

## Options considered

1. **Firestore.** Free at the start and serverless. Integrity rules (versions, references, deletion by player) move into application code, and analytical queries are poor.
2. **PostgreSQL with an ORM (TypeORM).** Widely used. TypeORM relies on legacy decorators with `reflect-metadata`, which Node cannot run without a build step, and it pushes towards using persistence entities as domain objects.
3. **PostgreSQL with a typed query builder (Kysely).** SQL stays visible, results are typed, no code generation, built-in migrations. Mapping between rows and aggregates is written by hand in the adapters.
4. **PostgreSQL plus a search engine (OpenSearch or Elasticsearch).** Better relevance and facets at very large scale, at the cost of a second store to keep in sync and a second place to delete personal data.

## Decision

Option 3.

- **Engine:** PostgreSQL.
- **Access:** Kysely in `packages/db`, with its migrator. Raw SQL through its `sql` template where needed (`tsvector`, `LISTEN/NOTIFY`).
- **Schema:** normalized tables per aggregate (for Game: `rooms`, `room_players`, `games`, `game_players`, `game_dilemmas`, `answers`), not one JSON document per aggregate, so integrity and deletion by player are enforced by the database.
- **Aggregates and persistence:** each aggregate exposes `toSnapshot()` and `static restore(snapshot)`. Adapters map rows to snapshots and back; the domain never imports anything from persistence. In-memory repositories store snapshots too, so unsaved changes are lost exactly as with the database.
- **Ids:** generated by the application through an `IdGenerator` port (UUIDs in production, sequential in tests). The database stores them and never creates them, because aggregates need their id when they are built and events carry ids before anything is saved. UUID v4 or v7 is decided with the provider.
- **Listings and search:** in PostgreSQL, with indexes, cursor pagination, full-text search per language and `pg_trgm`. A search engine is reconsidered only if relevance or scale demand it, as one more adapter.
- **Contract tests:** shared between in-memory and PostgreSQL adapters, run in CI against a PostgreSQL service container.
- **Not used:** an ORM, and GraphQL. GraphQL is reconsidered with the first read-only screen served over HTTP (history, catalog or personal data); the real-time core stays on WebSocket.
- **Provider:** decided together with hosting in ADR 0003. Cloud SQL is the natural candidate on GCP but has a minimum monthly cost; that is the trade-off to measure.

## Consequences

- Easier: integrity, deletion by player and dataset queries live in the database; SQL is learned for real; the domain stays independent of persistence.
- Harder: mapping between rows and snapshots is written by hand; schema changes need migrations; aggregates must keep `toSnapshot()` and `restore()` complete.
- Watch: `restore()` rebuilds without creation rules and must not emit events; snapshots are not a public API outside the context; the PostgreSQL adapter must pass the same contract tests as the in-memory one.
